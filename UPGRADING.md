# Installation and upgrades

Laravel v0.1.0 is the released baseline. The adoption additions below are unreleased. The local qualification descriptor still uses `0.1.0-RC1` solely to identify an exact review archive; it does not select a future release number. Follow [candidate installation](docs/release.md) and [configuration](docs/usage.md#install-and-configure).

Back up the application database and encryption keys before applying package migrations. Automatic discovery loads package migrations, including the observed-routing additions and the adoption tables. Migrations are reversible for a clean uninstall, including removal of package history; rollback is not an offboarding workflow and must not discard unresolved financial evidence. Rehearse changes against a disposable copy of the application's data.

## Upgrading from 0.1.0

Managed subscription Coupons add `withCoupon()`, `applyCoupon()` and `removeCoupon()`. Replace direct raw `discounts` creation options with `withCoupon($couponId)`. Newly prepared valid single top-level hosted Coupon instructions enter the same managed proof flow; stacking and nested/item discounts are refused. Existing raw hosted operation rows keep their original unverified contract and cannot use `removeCoupon()` without original proof; see the legacy-row boundary in the [Coupon contract](docs/contracts.md#managed-subscription-coupons). Existing free-period and experimental first-charge intent identities remain unchanged. See the [Coupon contract](docs/contracts.md#managed-subscription-coupons) for supported durations, original-command removal and the documented ONCE-on-ACTIVE boundary.

Update the application lock to the package’s new SDK requirement, `jojeringnax/airwallex-php-sdk:^0.1.3`, before using the [three-stage credit workflow](docs/contracts.md#owned-invoice-credits). Run the existing operation-observation migration before adding lines. Existing Coupon and item commands keep their identities. Newly scheduled transitions retain a stronger financial baseline (shape v3); old v1/v2 plans are unchanged and can be explicitly cancelled/recreated before an attempted write.

The optional experimental [fixed first-charge discount](docs/contracts.md#fixed-first-charge-discounts) uses the Coupon API included in SDK v0.1.3 and operation-observation migration. Existing 100-percent/CUSTOM calls retain their signatures, intent hashes and behavior. Choose a FLAT/ONCE Coupon and approve its exact amount explicitly; Invoice attribution is a separate confirmation. Whether a new ONCE application affects subsequent Invoices on an already-ACTIVE Subscription needs provider/account proof, and ONCE is not an arbitrary future-phase selector.

Apply the pending migrations for persisted sweeps, subscription transitions and Payments customers, operations, instruments, intents, refunds, receipts and observations. Existing Billing mappings and financial history remain authoritative. If the application publishes migrations, compare the package's migration files with its recorded migration names before copying only missing files; preserve customizations and avoid duplicate table creation.

Review the new configuration keys against the application's published configuration, then rebuild its configuration cache and restart workers. Billing's `webhook.queue_connection` and `events.queue_connection` default to null and retain the application default. Payments uses separate environment/account/credentials and an opt-in `payments.webhook.enabled` receiver; a Billing organization, Source or signing secret is not a Payments identity. Provision the application's database queue/cache/lock tables when choosing that profile, and register the recurring commands in [operations](docs/operations.md) and [Payments recovery](docs/payments-webhooks.md).

Existing standalone `Billable` calls retain their contracts. Models already using Cashier should use `AirwallexBillable` for explicitly authorized Airwallex work and retain original-provider routes for historical renewals/refunds; see [coexistence](docs/adoption-handoff.md). Do not replace or infer Payments mappings from existing Billing or Stripe identifiers.

Invoice transactions, Coupons, Credit Notes and optional object-preserving views now share the required released SDK v0.1.3 baseline. Remove incompatible application-level SDK pins and update the lock; the package no longer supports v0.1.1/v0.1.2. Default array views remain unchanged. Enable `airwallex.preserve_response_objects` explicitly when object/list metadata proof is required, then qualify the installed application graph.

Use the restricted [renewal-restoration and transition contracts](docs/contracts.md#adoption-amounts-and-provider-routing) only for supported combinations. Imported/old scheduled subscriptions without the original saved bound cannot use renewal restoration. For indefinite AUTO_CHARGE restoration, pass the explicit original null triplet to `cancelAtPeriodEnd` before scheduling; previous omitted fields do not prove that intent. Existing finite calls and saved finite operations remain supported. New due transitions have a current-cycle dispatch guard; existing saved plans retain their original shape and must be explicitly cancelled/recreated before their first attempt to adopt it. Custom `applyTransition` overrides must accept the optional effective-time parameter. Custom subclasses overriding `Subscription::cancelAtPeriodEnd`, `SubscriptionManager::cancelAtPeriodEnd` or `SubscriptionSynchronizer::reconcile` must accept the new optional parameters; match the package signatures before loading them. Keep existing command keys, encrypted intents, reservations, receipts and event delivery IDs through upgrades and rollback planning; a restored prepared row does not prove a write was never sent.

## Identity, recovery and uninstall

Keep environment/organization, billable morph identity and remote parent/resource IDs stable. Credential rotation does not change mapping identity. Changing an established morph map or custom table layout needs a coordinated application data/schema migration. Do not repoint a local mapping to another remote Customer or organization. Published migrations/custom subclasses must preserve the package's unique and foreign-key constraints, immutable fields and casts.

The schedule-cap migration only backfills `scheduled_ends_at` from matching positively owned raw snapshot evidence with a valid scheduled flag/bound. It does not fabricate effective dates from stale unrelated columns. Inspect a scheduled subscription with missing proof and reconcile it; default access remains conservative. Existing receipts/operations/outbox rows are operational evidence and must survive ordinary upgrades.

During 0.x, documented breaking public changes require a new minor with release notes and migration guidance; patches preserve public behavior. Only the latest minor is maintained under the provisional policy. Before adopting another candidate/release, inspect its notes, run dependency audit and migrations/recipes on your qualified runtime/backends, and compare exact SDK/API/webhook versions. Reconfigure a webhook subscription's version explicitly when required; changing API headers alone does not migrate deliveries.

Before uninstalling, follow [offboarding and retention](docs/operations.md#retention-replay-and-offboarding): explicitly confirm intended cancellations, resolve held operations, retain lawful invoice/history access and recover pending receipts/events. Removing code or a billable never cancels remote subscriptions.

The observed-routing migration adds separate Subscription and Operation evidence columns and backfills only positively owned Subscription response values. `observed_routing` retains those values when later optional fields are omitted; raw snapshots still reflect the latest response. Foreign-route imports remain inspectable, but a retained contradiction prevents high-level financial writes until a canonical read positively establishes the configured routing.

### Optional ACTIVE Coupon orchestration

Run the additive operation-observation migration before invoking `applyFreePeriod` or `removeFreePeriod`. It adds nullable encrypted, hidden, set-once response evidence; existing operations need no backfill. Coupon retrieval is included in required released SDK v0.1.3 at `33881b46d696435dfbd370ec371e1fef5452ba44`; no development archive or capability override is needed.

Generic item helpers now reject subscription/item discount inputs because their item outcome checks do not prove discount effects. The same guard rejects a legacy never-attempted prepared item command before its first financial dispatch, retaining its immutable intent/request identity and recording the preflight rejection. Already-attempted originals retain their existing read-only recovery path; item confirmation does not establish discount effects. Use the dedicated bounded helper or separately qualified raw SDK orchestration. Newly saved due plans include discount observations in shape version 2; changed/expired discounts block before first write. Existing plans and prepared commands retain version-1 hashes; cancel/recreate an unattempted plan to adopt the stronger guard. See [the contract](docs/contracts.md#bounded-active-free-periods) for ambiguity, removal and entitlement boundaries.

## Duplicate-permitting creation retries

Run the additive retry-history migration before deploying this release. New creation keys may now supersede unknown-ID `in_flight` or `ambiguous` creations and release local reservations automatically. Same-key replay stays prohibited. Implement listeners for the [retry and late-locator observations](docs/operations.md#retrying-an-unknown-creation) if your application needs duplicate servicing. The package retains original financial history and never asserts provider noncreation. Payment Intent current-order uniqueness moves to nullable `order_reservation`; historical `merchant_order_id` stays immutable. Rollback to the older schema is refused once duplicate-order history exists.
