## Workflow map

All resource accessors are `$client->billing()->…`; native bodies/responses remain arrays. Common signatures: `create(array): array`, `retrieve(string): array`, `list(array = []): array`, `update(string,array): array`. The SDK owns validation and exact decoding; Laravel supplies only orchestration and ownership checks.

| Workflow / official source | SDK operation | Request / response / ownership proof |
| --- | --- | --- |
| [Customers](https://www.airwallex.com/docs/api/billing/billing_customers) | `customers()->create/retrieve/list/update` | Create uses persisted `request_id` and profile; Update has no request_id. Validate returned `id` against known identity and configured organization authorization. Never establish ownership by email. |
| [Subscriptions](https://www.airwallex.com/docs/api/billing/subscriptions) | `subscriptions()->create/retrieve/list/update/cancel` | Create: customer, collection method, items, request_id and explicit configured entity/collector; AUTO_CHARGE requires owned source. Check ID and `billing_customer_id`; unknown state is preserved. Cancel requires request_id + explicit `proration_behavior`. |
| [Subscription items](https://www.airwallex.com/docs/api/billing/subscriptions) | `retrieveItem(id,itemId)`, `listItems(id,query)` | Explicit parent/child IDs, `page`/`page_size`; validate each `subscription_id`. Fetch every page before atomic local replacement. |
| [Hosted checkout](https://www.airwallex.com/docs/api/billing/billing_checkouts) | `checkouts()->create/retrieve/update/cancel` | HOSTED, customer, mode, request_id, entity/collector and durable metadata. SUBSCRIPTION uses `line_items`; SETUP requires currency and omits `line_items`. Check canonical `billing_customer_id`, mode, collector and stored correlation; resulting `subscription_id`/`payment_source_id` is independently retrieved/owned. Update is metadata-only; cancel is bodyless. |
| [Payment Sources](https://www.airwallex.com/docs/api/billing/payment_sources) | `paymentSources()->create/retrieve/list`; subscription `update` | Verify `billing_customer_id` and `linked_payment_account_id`; Source external identity is an authorized Payments Method, not a Billing Customer. Source replacement may immediately retry the last failed invoice. No invented default/delete/detach API. |
| [Invoices](https://www.airwallex.com/docs/api/billing/invoices) | `invoices()->retrieve/list/retrieveLineItem/listLineItems` | Force customer filter, verify response customer/optional subscription, verify parent before subordinate reads. Expose nullable `pdf_url`/`hosted_url`. No inferred renewal or settlement. |

All rows use pin 2026-08-21. SDK endpoint metadata independently declares organization resource level, no on-behalf-of support and relevant `billing.*:read/write` permission. [Key authorization](https://www.airwallex.com/docs/developer-tools/api/manage-api-keys) and [login](https://www.airwallex.com/docs/api/authentication/api_access_token) must not be confused with Payments account selection. Use a nondelegated organization client. Owning organization is trusted deployment configuration; a collector ID neither establishes organization ownership nor grants permission. Credential rotation preserves local context.

[Billing settings](https://www.airwallex.com/docs/billing/configure-your-billing-settings) require activated/authorized Billing, eligible legal entity, linked collection account, supported currency/method and eligible owned source where applicable. Supply entity/collector explicitly rather than infer defaults or entitlement. The accepted [#39 policy](https://github.com/jojeringnax/airwallex-laravel/issues/39) follows the selected SDK v0.1.1 / API 2026-08-21 schemas: Subscription `legal_entity_id` and `linked_payment_account_id` are optional response fields; Checkout `linked_payment_account_id` is required and `legal_entity_id` optional. For high-level financial confirmation/preflight/recovery, validate every returned routing value against configuration; malformed/null or contradictory values fail. Optional omission alone does not invalidate a known action or correlated canonical recovery. Durable request intent is request evidence, never a fabricated response observation. Source customer/collector checks, canonical ownership/context, resource identity and original operation correlation remain required. Official [Subscriptions](https://www.airwallex.com/docs/api/billing/subscriptions) and [Billing Checkouts](https://www.airwallex.com/docs/api/billing/billing_checkouts) were rechecked on 2026-11-10 against the selected released schemas. Read-only import/reconciliation remains available for inspection under canonical owner/context checks; retained positive routing evidence still blocks financial actions on a known foreign route after optional omissions. No account observation of omitted fields is claimed. Price frequencies must be compatible; schema-valid payloads do not establish account eligibility.

## Representation, changes and dates

Request item quantities are positive int32 integers; observed response quantities are schema numbers decoded as exact strings. Preserve decimal money, unknown numeric text and extra fields through the SDK. Omitted/null/false/zero remain distinct. Timestamp strings retain timezone, offset and arbitrary fractional precision.

Existing item IDs permit quantity/metadata/deletion; changing price deletes the old item and adds `price_id`. Omitted existing items remain. Require explicit `default_proration_mode` (NONE/PRORATED/ALL) or per-item controls. Per-item CUSTOM uses exact string `proration_value.charge_amount`/`credit_amount`; billing_action and proration_date preserve SDK semantics. No package computation of proration, totals or effective item state. Unsupported observed item models block unsafe changes without revoking lifecycle access. Source update is an explicit financial action because of immediate invoice retry.

The selected Subscription response exposes `billing_cycle_anchor_at`, `recurring`, `currency`, `duration`, `days_until_due`, `default_tax_percent` and `enable_automatic_tax`; item responses expose `tax_percent`. The official [update contract](https://www.airwallex.com/docs/api/billing/subscriptions/update), rechecked on 2026-11-12 against released SDK schemas, describes RESET_CYCLE as changing the billing anchor and KEEP_CYCLE as retaining it. New local transition plans preserve these financial controls independently from naturally advancing current-period dates. This is a package precondition, not proof that an external mutation cannot race the final canonical read or that a future Invoice has the intended amount.

`cancel_at_period_end=true` schedules ending; only confirmed effective dates establish its local schedule cap. A retained unrelated finite bound cannot prove a newly scheduled period end; partial reads/rollovers cannot move an already confirmed schedule cap later. Do not infer subscription termination from ordinary recurring period rollover. Immediate cancellation uses the separate cancel action and explicit proration. [Dunning settings](https://www.airwallex.com/docs/billing/subscriptions/dunning) prevent any universal retry deadline or automatic CANCELLED assumption after UNPAID.

Lists return `items`, `page_after`, `page_before`; pass `page_after` as `page` with unchanged filters/context. `page_size` is 1–1000. Reject repeated cursors/IDs and incomplete pages rather than publish partial item sets. Item/line lists have no customer filters, so establish parent ownership first.

## Renewal restoration

Rechecked on 2026-11-12 against the official [Subscription update API](https://www.airwallex.com/docs/api/billing/subscriptions/update), selected API `2026-08-21`, and released SDK request schemas. The low-level request already represents false plus the explicit null `duration`, `remaining_duration`, `ends_at` triplet; omission leaves fields unchanged. [SDK PR170's revision-specific observations](https://github.com/jojeringnax/airwallex-php-sdk/blob/217666aa875a3d674c931ec36fe17f0895b5a00a/docs/sandbox-validation.md#subscription-restoration-and-next-cycle-price-observations) used SDK `757c1efe6a020fcb4ba791df72118eff50ac6abf`: finite/originally indefinite ACTIVE AUTO_CHARGE reversal, originally indefinite PENDING/IN_TRIAL/UNPAID reversal, one paid renewal after reversal, and one lower-Price next-cycle Invoice. False alone left the flag true in its control. CANCELLED rejected reversal; UNPAID reversal retained the outstanding unpaid Invoice.

The provider omitted cleared optional limit fields. Those omissions plus canonical false, original saved indefinite command intent and unchanged source/collection support the bounded restoration confirmation in [public contracts](contracts.md#adoption-amounts-and-provider-routing). Omission alone proves no intended lifetime. The short-cycle renewal experiments had zero-total stub first Invoices; one observed renewal proves neither unlimited recurrence, exact races nor settlement. The API and SDK remain stateless; Laravel owns original intent, access caps, concurrency and recovery. No SDK runtime change or new dependency floor is needed for these requests. The lower-Price case projected the new item immediately, then observed its next-cycle Invoice. This supports submitting NONE before renewal; it does not establish that a request submitted after renewal changes an already-created Invoice. Actual installed Laravel Sandbox journeys remain separate from the dated SDK observations.

## Signed events

[Signing](https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events) uses hex HMAC-SHA256 over exact x-timestamp bytes followed by raw body, endpoint secret and configured millisecond tolerance. Use SDK WebhookVerifier before SDK WebhookEvent decoding. Decoder preserves direct and `data.object` forms; it does not authorize envelopes or supply trusted normalization. Validate organization `org_id`, selected version, event family and resource identity independently. Do not alias account_id into org_id. A present malformed wrapper cannot fall back to direct data. These are SDK-decoded identity guards, not native JSON token provenance: numeric identity tokens can decode identically to quoted strings, and duplicate keys retain the SDK codec’s last-wins behavior. The public WebhookEvent API does not expose stronger wire-type proof; canonical known mapping/customer/correlation verification remains mandatory. No custom parser or stronger wire-shape claim is introduced.

[Billing events](https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events/billing): subscription created/in_trial/active/unpaid/modified/cancelled; checkout created/completed/cancelled; invoice created/finalized/updated/payment.paid/voided. No Payment Source event is established. Generic/Billing examples disagree about owner/nesting/version; quarantine unsupported/missing/conflicting proof, retain classification and reconcile canonically. Valid signatures alone never associate an unknown resource. [Public contracts](contracts.md) own receipt storage, recovery and event delivery.

## Evidence gaps and verification actions

- SDK Checkouts has no list method. Unknown-ID creation recovery needs verified metadata correlation from a signed event or explicit operator-known ID plus ownership/intent verification. Retain ambiguity otherwise; an upstream list capability would improve automatic recovery. Do not implement transport in Laravel.
- SDK v0.1.1 normalizes populated JSON objects to PHP arrays; numeric-only object keys can become indistinguishable from a JSON list. Released SDK v0.1.2 includes [PR #157](https://github.com/jojeringnax/airwallex-php-sdk/pull/157)'s opt-in object-preserving HTTP and WebhookEvent views. The optional `airwallex.preserve_response_objects` adapter uses those public views in both Billing and Payments, including pages and signed envelopes. It projects ordinary maps to existing array interfaces while retaining empty and numeric-list-shaped objects as `stdClass`; persistence retains that decoded proof. The default remains the released array representation. Without opt-in proof, ambiguity recovery retains the original operation without replay. Qualification now selects released v0.1.3 with the option enabled under [read-proof follow-up #37](https://github.com/jojeringnax/airwallex-laravel/issues/37). The opt-in view does not establish native numeric-token provenance or duplicate-key rejection; no Laravel decoder is introduced.
- No documented request_id lookup, safe replay window, proof of resource absence or universal retry/cancellation deadline exists. Timeout, expired lease and 404 do not authorize a replacement financial write.
- Checkout expiry prose and observed Sandbox timestamps differ; use returned status/dates, never guaranteed TTLs. Completed checkout notifications and resulting source/subscription availability remain account-specific observations.
- Invoice API/product guides describe different link-expiry clocks; renewal on retrieval is unverified. Return links as observed, including null/expired values, without a local clock or renewal promise.
- Account activation/permissions, collection eligibility, natural trial/renewal/ending timing, configured dunning, actual settlement and cleanup are not established by deterministic fixtures. Record opted-in Sandbox results separately under [compatibility evidence policy](compatibility.md).
- Restoration remains limited to the [supported saved-intent combinations](#renewal-restoration). Reactivation, link regeneration, PDF rendering/mailing and broad resume conveniences remain unclaimed. No newly demonstrated SDK capability blocker was found for the accepted v1 operations; fresh metadata equality above remains evidence work, not a provisional provider fact.

Validation must cover success and malformed/foreign-ID/owner/version cases with real SDK decoding, precise numbers/dates, direct/wrapped events, all-page failure, stale history, timed-out writes and queue recovery. Sanitized fixtures must name the selected version and be described as synthetic contract fixtures, never provider observations.

## Native Coupon free periods

The official [Coupon workflow](https://www.airwallex.com/docs/billing/billing-components/coupons/coupons-via-api), rechecked on 2026-11-13 with selected SDK `33881b46d696435dfbd370ec371e1fef5452ba44`, demonstrates FLAT amount/currency with ONCE duration. The [Coupon overview](https://www.airwallex.com/docs/billing/billing-components/coupons/coupons) describes subscription redemption at creation, duration from the first billing cycle and ONCE on the first Invoice. Subscription updates permit discounts and describe future billing, but these sources do not resolve whether a newly applied ONCE Coupon discounts any later Invoice on an already-ACTIVE Subscription with prior Invoices. That eligibility and the target Invoice, including intervening adjustments, remain explicit provider/account questions. A caller-selected reduction can leave a paid remainder only when actual attributed Invoice evidence establishes it. Invoice `total_discount_amounts.applied_discount_id` and `applied_discounts` can represent the original subscription Discount; the package requires that exact identity rather than accepting a cloned Invoice Discount. [Fixed first-charge discounts](contracts.md#fixed-first-charge-discounts) define the experimental primitive and positive proof; natural timing, tax and collection remain unobserved.

Official [Coupon API](https://www.airwallex.com/docs/api/billing/coupons), [Coupon workflow](https://www.airwallex.com/docs/billing/billing-components/coupons/coupons-via-api) and [Subscription API](https://www.airwallex.com/docs/api/billing/subscriptions) were inspected on 2026-11-12, together with released SDK v0.1.3 revision [`33881b46d696435dfbd370ec371e1fef5452ba44`](https://github.com/jojeringnax/airwallex-php-sdk/tree/33881b46d696435dfbd370ec371e1fef5452ba44). Its selected contracts retain API 2026-08-21. Coupons are organization resources; present context fields must agree with configured ownership. Coupon `expires_at` limits redemption, while an applied CUSTOM Discount's `ends_at` identifies its own expiry. Percentage and duration remain SDK-decoded exact values.

The documented Subscription update replaces the supplied subscription-level discount set; an empty list removes that level's discounts. One Coupon is supported per subtotal, separately from item discounts. The package's bounded discount helper selects an active 100 percent CUSTOM Coupon and proves the returned/canonical Discount identity and bounds. SDK validation, redemption, calculations and natural expiry remain provider-owned. The [SDK source contract](https://github.com/jojeringnax/airwallex-php-sdk/blob/33881b46d696435dfbd370ec371e1fef5452ba44/docs/billing-resources.md#coupons-and-one-off-invoice-application) contains pre-publication wording; the [v0.1.3 release record](https://github.com/jojeringnax/airwallex-php-sdk/releases/tag/v0.1.3) supersedes that wording and confirms published availability.

These inspected contracts and deterministic fixtures establish the discount command, not an account observation of a billing holiday or a charge for only the paid days. No Coupon mutation or zero-cash renewal Invoice was observed in this Laravel case. Exact expiry/renewal races, already-finalized invoices, arrears/prepaid entitlement, taxes and settlement require separate account qualification. The [partial-period requirement](scope.md#catalogue-coupons-and-access) and financial alternatives are retained in [question #101](https://github.com/jojeringnax/airwallex-laravel/issues/101); [#54](https://github.com/jojeringnax/airwallex-laravel/issues/54) retains unsupported required guarantees and [#63](https://github.com/jojeringnax/airwallex-laravel/issues/63) owns account validation.

The official [subscription-management guide](https://www.airwallex.com/docs/billing/subscriptions/get-started-with-subscription-management), rechecked on 2026-11-12, states that discounts are not separately prorated: they apply to configured invoice lines or the subtotal. Its item-change examples distinguish credits against an existing in-advance Invoice from charges for time active on an in-arrears item. These are documented billing effects, not proof of a cash refund or this account's behavior.

The official [Subscription update API](https://www.airwallex.com/docs/api/billing/subscriptions/update), rechecked on the same date, documents automatic `PRORATED` item charge/credit calculations and per-item `CUSTOM` exact charge/credit amounts. `proration_date` selects a calculation time within the current billing period; it does not schedule a later change. The [released SDK v0.1.2 financial-control contract](https://github.com/jojeringnax/airwallex-php-sdk/blob/v0.1.2/docs/billing-resources.md#choosing-subscription-financial-controls) already exposes these controls without calculating amounts; they are also included in the required released SDK baseline. They are candidates for the partial-period strategy, not proof of a complete free-interval workflow, a particular Invoice amount or handling of an already-paid period. Keep those outcomes open until the chosen sequence and actual financial effects are qualified.
