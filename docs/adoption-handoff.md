# Application integration guide

Use these patterns to integrate the library into a Laravel application after selecting compatible package/SDK versions. [Scope](scope.md#full-provider-adoption-contract) owns required scenarios and ownership; [public contracts](contracts.md) own package behavior. [Tracker #46](https://github.com/jojeringnax/airwallex-laravel/issues/46) and [handoff issue #65](https://github.com/jojeringnax/airwallex-laravel/issues/65) own library delivery status, exact candidate references and unresolved provider evidence. Application migrations and deployments are separate integration projects.

## Application work packages

The following are examples of application responsibilities, not a prescribed application architecture or staffing plan. Select the applicable work and assign ownership within the integrating application.

| Owner / work package | Concrete change and evidence needed |
| --- | --- |
| Backend integration owner: provider entry point | Introduce explicit Billing and Payments services around an authorized original billable. Preserve Cashier's methods, relations, provider IDs and internal dispatch. Route by server-owned resource/cohort; version client APIs and reject arbitrary provider/account selection. Exercise current/history, new commands, recovery and old-provider refunds on the same model. |
| Migration owner: identities and history | Add provider-qualified customer/subscription/intent/refund references without rewriting legacy IDs. Inventory original providers, exact owner/context, active generations, command keys, reservations and unsettled obligations. Backfill only explicit verified associations; email/name matches do not establish ownership. Keep legacy reports and refunds readable. |
| Commercial/backend owner: catalogue and entitlements | Build immutable environment/currency/cadence price aliases and compare actual amounts. Implement discounts, redemption and free-period rules when the application needs them. For a migration, inventory historical native discount IDs and required percentage/fixed/repeating behavior. Required native discounts need separately selected SDK support. Date application entitlements independently of deferred billing hints; explicitly accept worker lateness or keep the scenario unavailable. |
| Web/mobile owners: client contracts | Replace provider-specific setup/payment APIs and UI with authenticated versioned contracts. Implement embedded consent, shopper-present card/wallet/3DS, return URLs/deep links and cancellation/error states. Register/verify eligible wallet domains and native SDK configuration. Browser success alone never completes an order; keep transient client secrets out of durable client/server logs. Qualify supported browser, mobile and admin clients independently. |
| Finance integration owner: ledgers/accounting | Keep commercial invoice issuance, cash allocation, credit notes, refunds and provider clearing configuration explicit. Use canonical successful financial identities and exact amounts; deduplicate distinct deliveries and Billing/Payments references to the same underlying resource. PAID invoices, credits, manual/out-of-band observations, partial capture and pending/failed refunds have separate outcomes. Missing allocation proof remains unresolved. Reconcile historical reports and verify real accounting mappings. |
| Commercial/platform owners: instruments | Default to explicit recollection. Optional provider-assisted transfer requires both processors' approval/export process, completed merchant KYB and transfer report; match its original customer/card identifiers to authorized local owners and verify resulting account-owned Customer/Consent/Method. Quarantine unmatched/failed rows. Never copy processor tokens or silently recreate active subscriptions. |
| Platform owner: deployment and operation | Select a profile supported by [compatibility](compatibility.md) and verify the application's PHP/framework/database, queue/cache/lock/supervisor topology, scheduler and encryption/signing configuration. Application runtime upgrades and deployment execution belong to the integrating team. |

## Cohorts and original-provider routing

Start with an explicitly selected cohort eligible for new Airwallex work. Existing Stripe subscriptions keep their original renewal/cancellation/refund/history route until a separately approved migration decision proves their replacement and billing boundaries. A customer may legitimately have one provider's old history and another provider's new subscription, but one business payable must retain its original provider, account and permanent command identity. Airwallex Billing Sources and Payments Consents remain distinct even on the same application customer. A migration status flag cannot reassign a historical financial resource.

Keep application feature flags separate for new subscription starts, due transitions, new Payments intents and refunds. Rollback stops the affected new work while preserving receipt acceptance, canonical read recovery, ledger/outbox retries and investigation of already-attempted actions. A rollback never generates a fresh action key for an uncertain command, moves a refund to another provider or deletes a reservation to force progress. Unattempted due plans may be cancelled only through their documented local action; attempted plans keep their original identity and obligations.

## Isolated rehearsal and resumption

1. Select the exact reviewed package and SDK commits, install their immutable archives with the [qualification driver](release.md#adoption-tracks-and-an-unreleased-sdk), and retain archive hashes, manifests, consumer lock, advisory audit and actual runtime/backend reports. Run subscription and Payments tracks on the same final cumulative candidate. Qualify final tagged SDK/package provenance separately after release authorization; development archives are explicitly unreleased.
2. On a disposable copy of the actual target profile, rehearse migrations/rollback/reapply, provider discovery, cached configuration and workers/scheduler with synthetic deny-network transports. Register schedules through the application's configured Laravel scheduler entry point and verify that it is loaded. Verify queue connections/names and independently supervised worker/scheduler startup; schedule registration is not execution evidence.
3. Rehearse encrypted payload recovery and database backup/restore with original action/request IDs and exact constraints preserved. Restore the matching encryption-key material through the verified framework procedure; credentials may rotate without changing immutable Billing/Payments identities. Use a consistent database backup and validate old encrypted data before key rotation. Never print keys, raw customer profiles, signed bodies or client secrets as evidence.
4. After any restore, keep financial submission/due workers stopped until the post-backup command interval is reconciled against the application's durable command journal and provider evidence. A restored `prepared` row may predate a real attempted request; it is not proof that replay is safe. Missing post-backup commands/IDs or unresolved remote outcomes remain a stop condition for new financial work. Canonical read recovery and retained ledger/history remain available under verified ownership.
5. Bind separately authorized [subscription](sandbox.md#adoption-gate-63) and [Payments](https://github.com/jojeringnax/airwallex-laravel/issues/64) account journeys to that exact graph. Preserve original failed/pending results and cleanup obligations; repeat affected scenarios after changes. Natural renewal/dunning/boundary behavior, browser clients and external accounting cannot be replaced by synthetic fixtures.

Each integrating application verifies its own deployment profile and rehearsal. Synthetic SQLite/MySQL library checks do not establish an application's web/worker/scheduler parity. Production rollout and library release publication are separate from these integration examples.

## Operators and alerts

The platform owner must assign an on-call owner and measurable, environment-specific thresholds before rollout. Alert on last successful full sweep age/cursor progress, stale projection age, oldest pending/failed receipt and outbox age, failed queued listeners, expired processing leases, blocked due transitions and unresolved ambiguous/acknowledged financial operations. Count and age unresolved obligations; job dispatch success alone is not processing/listener completion. Route ownership/version conflicts to the integration owner and financial ambiguities/allocation mismatches to the finance owner.

Investigations use safe local IDs, context classifications, exact candidate references and the private ownership/command journal. Preserve the original action/request ID, canonical resource identity and observed outcomes. Use the [recovery runbook](operations.md#uncertain-actions); unavailable evidence stays pending. Restore drills and operator incidents must demonstrate that read recovery cannot become financial replay. An application rollout requires its own integration/client/accounting checks, deployment rehearsal and applicable account validation. These application checks are separate from the library documentation deliverable in issue #65.
