# Public interfaces and persistence contract

This reference describes the released implementation contract and explicitly identified adoption interfaces. Accepted invariants are in [scope](scope.md); public choices are accepted under [#34](https://github.com/jojeringnax/airwallex-laravel/issues/34), support under [#10](https://github.com/jojeringnax/airwallex-laravel/issues/10), and provider facts under [provider contracts](provider-contracts.md). The [consumer guide](usage.md) links executable recipes; [release qualification](compatibility.md#release-evidence) defines their evidence requirements.

## Consumer API

Optional `airwallex.preserve_response_objects` is a strict boolean, default false. Enabling it selects the object-preserving HTTP and WebhookEvent views in the required released SDK v0.1.3 baseline. The package projects ordinary decoded object maps into its existing array interfaces while retaining empty and numeric-list-shaped objects as `stdClass`, so object/list metadata proof survives reads and persistence. Both Billing and Payments, their pages and signed envelopes follow this projection. SDK decoding, exact numbers, signatures and raw-token/duplicate-key limits remain SDK-owned. Default array behavior remains supported; qualify the selected representation in the installed application.

Applications authorize the local billable first. Any persisted Eloquent model uses `Jojeringnax\AirwallexLaravel\Billable`; keys may be integer/UUID/ULID and morph maps remain effective. Methods do not assume an authentication guard. `airwallexProfile(): array` is overridable and returns provider customer profile keys; saving a model never syncs remotely.

```php
$customer = $team->createOrGetAirwallexCustomer('customer-command-123', ['name' => 'Team']);
$customer = $team->linkAirwallexCustomer($remoteCustomerId);
$customer = $team->syncAirwallexCustomer('profile-command-124', ['email' => null]);

$subscription = $team->newSubscription('default', $priceId)
    ->quantity(5)->trialDays(7)->startsAt('2026-12-01T00:00:00Z')
    ->create('subscribe-command-125', ['collection_method' => 'AUTO_CHARGE', 'payment_source_id' => $sourceId]);
$checkout = $team->newSubscription('support', $supportPriceId)
    ->quantity(2)->checkout('checkout-command-126', ['success_url' => $successUrl, 'back_url' => $backUrl]);
return $checkout->redirect(); // Explicitly expose the provider HOSTED URL.

$setup = $team->setupPaymentMethod('setup-command-127', ['currency' => 'USD', 'success_url' => $successUrl, 'back_url' => $backUrl]);
$setup->reconcile(); // Verifies checkout and resulting source; does not grant access.
$sources = $team->paymentSources(); // All pages, owned customer/collector.
$checkout->reconcile(); // Verifies resulting subscription under its reserved name.
$checkout->updateMetadata('metadata-command-128', ['reference' => 'support']);
$checkout->cancel('cancel-checkout-command-129'); // SDK action is bodyless.

$subscription = $team->importSubscription('default', $remoteSubscriptionId);
$subscription->updatePaymentSource('source-command-130', $sourceId);
// Explicit action: may immediately retry the provider's last failed invoice.
$subscription->updateQuantity('quantity-command-131', 6, ['default_proration_mode' => 'NONE']);
$subscription->updateQuantity('item-command-132', 3, ['default_proration_mode' => 'PRORATED'], $itemId);
$subscription->swapPrice('swap-command-133', $newPriceId, ['default_proration_mode' => 'PRORATED'], $itemId);
$subscription->addItem('add-command-134', $anotherPriceId, 1, ['default_proration_mode' => 'NONE']);
$subscription->removeItem('remove-command-135', $itemId, ['default_proration_mode' => 'NONE']);
$subscription->updateItems('custom-command-136', [['id' => $itemId, 'quantity' => 3, 'proration_mode' => 'CUSTOM', 'proration_value' => ['charge_amount' => '100.00', 'credit_amount' => '20.00']]], ['billing_action' => 'IMMEDIATE_CHARGE_AND_KEEP_CYCLE']);
$subscription->cancelAtPeriodEnd('ending-command-137');
$subscription->cancelNow('cancel-command-138', 'NONE');
$subscription->reconcile();

$team->subscription('default'); // Current, otherwise latest history for inspection.
$team->subscribed('default'); // Current only, no HTTP.
$subscription->active(); $subscription->onTrial(); $subscription->valid(); $subscription->onGracePeriod();
$invoice = $team->findInvoice($invoiceId);
$invoices = $team->invoices();
$invoice->pdfUrl(); $invoice->hostedUrl(); $invoice->lineItems(); $invoice->lineItem($lineItemId);
$subscription->invoices();
```

For an existing Cashier model, `new AirwallexBillable($authorizedPersistedModel)` exposes these Billing methods through a separate object. It retains the original model's morph class/key and optional `airwallexProfile()` without adding another trait or delegating to its `subscription`, `subscriptions`, `newSubscription`, `invoices`, `findInvoice` or setup methods. The original model keeps all Cashier contracts; returned Airwallex Subscription/Checkout objects retain their package lifecycle/recovery methods. Construct a wrapper after authorization for each request; it does not authorize the model itself. Unsaved models are rejected. [Coexistence usage](usage.md#cashier-coexistence) explains the installed-consumer qualification. No Cashier runtime dependency is added, and the standalone Billable trait remains unchanged.

`newSubscription(name, priceId)` requires a nonempty explicit name. `addPrice(priceId, quantity)` supports multi-item creation. Request quantities are native positive integers under the SDK schema; observed response quantities remain exact decimal strings, including fractional values. Unsupported observed item shapes block unsafe item changes, not otherwise valid lifecycle access. Quantity inputs remain uncoerced until native integer validation; non-strict PHP callers cannot truncate floats. Single-item conveniences fail when the target is ambiguous; multi-item changes require the item ID. Price swaps use deletion plus addition, never an immutable item price update. `swapPrice` accepts an optional final integer quantity after itemId; without it, a fractional/oversized observed quantity is refused rather than truncated. Caller options cannot override mapped customer/context, durable request identity or managed items. `trialDays(days)` uses the final explicit `startsAt` as its anchor, or the intent-preparation time when absent, independently of builder call order. Omit starts_at when the caller does not supply it, preserving the provider default. trialDays produces an absolute trial end at intent preparation; delayed hosted completion does not guarantee that many days after completion. Persist the resulting absolute dates in the prepared intent; repeated action keys reuse them rather than shifting a trial with the clock.

`trialUntil(string|DateTimeInterface $endsAt)` supplies an absolute trial end for direct and hosted subscription creation. It is mutually exclusive with `trialDays()`, must follow the explicit start or intent preparation time, and preserves string offset/fractional text. Its exact input is part of the immutable builder specification. Existing builders without an explicit end retain their original specification shape and repeated-key behavior.

`actionKey` is a stable application command identifier, scoped to immutable billing context. When `createOrGetAirwallexCustomer` finds an already confirmed mapping, it performs a local read: supplied profile values do not sync, a fresh key remains unused, and unrelated mutation holds remain intact. An already-recorded key still validates its original mutation intent and resolves any original ambiguity; use explicit customer sync to update profiles. Persist it in application command handling. Same key/intent returns or recovers the same operation; changed kind/target/payload conflicts. A distinct user-authorized financial action needs a new key. Ambiguous operations throw an actionable exception containing the safe local operation ID; they never silently reissue the write. Customer and Subscription methods return the configured corresponding Eloquent model after canonical verification. `setupPaymentMethod` returns the configured Checkout; `paymentSources` returns a collection of immutable lightweight `PaymentSource` objects (remote `id`, `billingCustomerId`, `linkedPaymentAccountId`, sanitized provider data), with no source table. `updatePaymentSource` returns the reconciled Subscription. Checkout methods return the configured Checkout, invoice reads return immutable lightweight Invoice objects, and list reads return collections after all pages succeed. Unmapped billables return no local subscription; remote operations require a confirmed customer.

Public package exceptions extend `BillingException` (RuntimeException): `ConfigurationException`, `OwnershipException`, `ConflictException`, `EvidenceException` and `AmbiguousOperationException`. Messages contain safe classifications only; `AmbiguousOperationException` exposes readonly string `operationId` and retains only already-redacted SDK exceptions as causes, preserving SDK classification. Untrusted transport/storage/confirmation causes are discarded; default string/debug output excludes traces/arguments and exception serialization is rejected. `ConflictException` may expose a nullable readonly `operationId`; other exceptions need no payload/context dump. SDK exceptions retain their original classification as causes; no secret payloads are added. Raw SDK `Client` is replaceable in the container; `Airwallex` facade resolves it. `BillingContext` is immutable environment/organization; credentials never form database identity. Provider access policy interface is `SubscriptionAccessPolicy::allows(Subscription $subscription): bool`, replaceable through the container. Default lifecycle helpers follow [scope](scope.md), independently of custom policy.

High-level financial workflows use one configured legal entity/collector, as accepted in [#39](https://github.com/jojeringnax/airwallex-laravel/issues/39). Different routing overrides and contradictory returned routing values are rejected. Subscription routing fields are optional; Checkout requires `linked_payment_account_id` but may omit `legal_entity_id`. Missing optional fields alone do not block known actions, reads or correlated recovery. Original request intent, owned canonical resource/customer/context and operation correlation still govern confirmation; timeout or unknown identity never permits replay. Snapshots retain absent fields without filling them from configuration. `observed_routing` separately retains the last positive Subscription routing values across omissions, so a read-only foreign-route import cannot erase a known contradiction and authorize a financial write. A new positive canonical value replaces that field’s prior evidence. Operations separately retain bounded routing values from mutation responses; a previously returned contradiction or malformed value needs positive matching canonical evidence, rather than omission, before recovery can succeed. Entity/collector eligibility and financial outcomes remain provider/account evidence.

Scheduled access uses `scheduled_ends_at`, a local projection copied from positively observed effective-bound dates while the scheduled flag is true. A previous unrelated finite end does not prove a fresh schedule. Retain the earliest confirmed schedule cap across partial reads/rollovers; an explicit false flag resets this schedule projection. Ordinary ACTIVE rollovers still do not cap access. [Question #34](https://github.com/jojeringnax/airwallex-laravel/issues/34#issuecomment-6770070532) records the evidence and data effects.

## Schema ownership

All tables use `airwallex_`; local primary keys are ULID strings. Configured subclasses extend the corresponding package model; the service provider resolves all relationships and service queries through configured classes. Local Laravel timestamps are UTC microseconds. Provider dates/timestamps are exact text with timezone/offset/fraction retained; a chronological comparator handles arbitrary fractional precision. JSON snapshots preserve SDK-decoded unknown fields and decimal strings; populated numeric-key object wire types may already be normalized by the SDK ([#37](https://github.com/jojeringnax/airwallex-laravel/issues/37)), so those ambiguous updates require further proof rather than inferred confirmation; raw owner/profile data and secrets are hidden from normal model serialization.

DB constraints enforce uniqueness; services validate parent/context on every attach. Offboarding never automatically deletes history or performs remote cancellation; application retention/authorization decides local deletion after operational and legal review. Customer/subscription deletion is restricted while children/reservations exist.

## Operation, checkout and receipt lifecycles

Operations: `prepared` persisted before I/O, then `in_flight`, then `succeeded`, `failed` (verified no-write rejection), `ambiguous` (unproved request/outcome), or `acknowledged` (known item-write response, requested observable item state not yet proven). Preserve original request/correlation and record returned remote identity before follow-up reads. For eligible item actions only, acknowledged releases the active mutation mutex while preserving exact request/intent/result IDs; same-key calls and recovery read only. Unknown HTTP outcomes stay ambiguous and held. Exact native-integer versus observed decimal quantity proof distinguishes 5.000 from 5.00000000000000001 without floats. New item proof needs fresh owned references and remains unconfirmed while overlapping unresolved item actions make attribution ambiguous; old/new coexistence does not prove removal, active fee or settlement. Later separately authorized actions never authorize replay of the earlier one. [Question #40](https://github.com/jojeringnax/airwallex-laravel/issues/40) records this accepted defensive lifecycle choice. Never hold a DB transaction over network calls. Unique rows and compare-and-set transitions coordinate competing writers. On MySQL, short local transactions lock the owning Customer before reservation/projection reads and retain receipt-lease fences through projection commits; provider I/O remains outside those transactions. An expired worker lease is recovery eligibility, not permission to replay a financial write. Known-ID operations recover through canonical reads; unknown-ID create requires verified metadata correlation or an explicit operator-supplied resource and ownership proof. A 404 or timeout alone cannot release the name. The SDK exposes no checkout list; record the specific upstream automation limit rather than adding Laravel HTTP.

A Checkout reserves its subscription name from intent through confirmed resulting Subscription or verified terminal cancellation/expiry without a resulting resource. Ambiguous terminal evidence retains the reservation. Store actual provider status/expiration; do not invent TTLs. Setup has no name slot and its completed verified source does not change subscription eligibility. Delayed responses and webhooks converge through operation correlation and immutable IDs. Caller metadata is merged with a reserved operation marker; overriding it is rejected.

Receipts: `pending`, `processing`, `processed`, `ignored`, `quarantined`, `failed`. Verify signature with the SDK before persistence; bind trusted receiver context/version; durably store before 200. Foreign owner/version or conflicting identity is quarantined; unknown events/resources are ignored with reason, never adopted. Dispatch failure leaves pending work; scheduled replay finds it. Workers claim receipts atomically and recover expired processing leases. Signature verification occurs on receipt, not replay; replay trusts the already verified encrypted receipt. Purge bodies only for terminal processed/ignored/quarantined receipts after configured retention (default seven days); pending/processing/failed bodies remain recoverable until processed or explicitly quarantined by an operator. Retain identity/digest/outcome for deduplication. A purged receipt cannot be replayed from its body; canonical reconciliation remains available.

Domain events use a stable correlation ID, local resource ID, context and prior/current provider status, never credentials, profile data or URLs. `SubscriptionReconciled`, `CheckoutReconciled`, `InvoiceObserved` and `WebhookProcessed` are persisted in `airwallex_domain_events` in the state-change transaction, then dispatched after commit. A failed dispatch or crash between commit and dispatch leaves the outbox row undispatched; the scheduled event command retries it. A crash after listener delivery but before marking dispatch can redeliver the same stable ID. Outbox delivery is at least once; application listeners deduplicate stable IDs and reconcile if delivery was interrupted. For Laravel ShouldQueue listeners, outbox acknowledgement means successful queue handoff, not eventual listener completion; Laravel queue retry/failed-job handling owns that separate stage. No exactly-once financial/listener promise is made.

## Invoice transaction observations

`Invoice::transactions(array $query = []): Collection<InvoiceTransaction>` reads every cursor page for that exact invoice; `transaction(string $id): InvoiceTransaction` verifies a direct lookup against the same freshly retrieved parent. Parent/customer/context/routing is rechecked after remote I/O; absent invoice/customer linkage cannot be adopted. Foreign filters, repeated IDs/cursors and incomplete pages produce no partial collection. Optional external/collector/type/out-of-band omission remains visible, and every present route must match configuration. Ordinary JSON/debug output includes only identities, exact amount/currency and classifications; explicit `toArray()` preserves sanitized SDK observations and unknown fields. `identityKey()` is stable for provider/environment/owning Billing organization/transaction ID/type across distinct observation-event IDs; it is not proof of a successful cash allocation.

This API uses the required released SDK v0.1.3 baseline; no additional dependency selection is necessary. The [selected SDK transaction contract](https://github.com/jojeringnax/airwallex-php-sdk/blob/v0.1.2/docs/billing-resources.md#billing-transactions) does not prove the transaction total is exclusively allocated to one invoice or settled. PAID invoices may be covered by credits/adjustments; a pending/failed/refund/out-of-band transaction is not a new provider cash payment. Applications retain independent allocation/currency-conversion evidence and deduplicate ledger posts by verified financial identity. No application accounting row or cash ledger is introduced by the package.

## Managed subscription coupons

`SubscriptionBuilder::withCoupon(string $couponId)` freezes one existing Coupon for `create()` or `checkout()`. It is an additive builder definition field only when selected; existing builders keep their prior intent hashes. Direct raw `discounts` is managed. A valid single top-level hosted Coupon instruction remains supported through normalization and the same proof; already-recorded raw intents keep their specification/defaults and are not retroactively rewritten. New raw hosted FLAT selection requires explicit currency; nested/item discount input and stacking are refused.

`Subscription::applyCoupon(string $actionKey, string $couponId): Subscription` applies a subscription-level PERCENTAGE or FLAT Coupon to the current undiscounted ACTIVE generation. CUSTOM and INDEFINITELY are supported; ONCE on existing ACTIVE is refused under the documented first-invoice boundary. `removeCoupon(string $actionKey, string $originalActionKey): Subscription` removes the exact Discount from an original managed direct creation, hosted creation or application command on current PENDING/IN_TRIAL/ACTIVE. Legacy bounded free-period and experimental first-charge commands retain their own removal helpers.

The operation stores normalized model, exact percentage/amount, currency, duration and redemption deadline. FLAT currency must agree with the explicit subscription currency and every canonically retrieved creation Price; changes use the canonical subscription currency. Terms are reread before the first write, and expired or changed financial terms refuse dispatch. Coupon administration, commercial eligibility, redemption and calculations remain SDK/provider/application responsibilities.

`airwallex_operations.observation.discount_proof` contains a set-once original Discount identity, created/start times and optional CUSTOM end. Direct writes record response identity before canonical reads; a matching later Coupon cannot manufacture a missing original identity. Hosted sessions expose no resulting Subscription at creation: their first complete owned resulting Subscription reads establish the original Discount before local association and event dispatch. All canonical item pages must be free of competing item discounts. Later expiry/removal preserves historical proof and cannot independently deny an otherwise eligible Subscription. Proof is encrypted and hidden through the existing observation cast; no migration is added.

ONCE applies to the provider's first invoice; CUSTOM is a calendar interval, not local discount-count arithmetic. The package does not prorate discounts, calculate taxes or infer invoice/cash settlement. Template create/update/archive remains application-owned through `billing()->coupons()`.

## Bounded ACTIVE free periods

This interface applies a 100 percent discount. Its name does not imply that it calculates a free calendar interval or charges the paid remainder. The [partial-period requirement](scope.md#catalogue-coupons-and-access) remains under strategy #101; this helper alone is not its implementation. Its actual Invoice effects still require account evidence.

`Subscription::applyFreePeriod(string $actionKey, string $couponId): Subscription` applies one subscription-level native Coupon to the current ACTIVE generation. The application authorizes eligibility and selects the Coupon; this package creates no catalogue or commercial redemption policy. Coupon retrieval is included in required SDK v0.1.3 at `33881b46d696435dfbd370ec371e1fef5452ba44`.

The selected Coupon must be active, exactly 100 percent PERCENTAGE, CUSTOM with a positive DAY/WEEK/MONTH/YEAR duration, and available for redemption. Before the first write the package verifies unchanged Coupon terms, current name generation, ACTIVE state, recognized collection method, no scheduled cancellation, no existing subscription-level discounts, and a freshly owned Source for AUTO_CHARGE. The durable encrypted original intent contains the Coupon ID/terms, original subscription shape and fixed NONE/DEFER_CHARGE_AND_KEEP_CYCLE controls. Generic item mutation options cannot apply/remove discounts, including stored never-attempted prepared payloads; use this qualified command or explicitly qualified raw SDK orchestration.

Confirmation requires the response and canonical reads to agree on exactly one owned subscription-level Discount: its ID, customer/parent, Coupon, exact percentage/duration, creation/effective-start times and a consistent positive end. `Operation::observation` stores the original response proof as encrypted hidden data, set once without changing immutable command intent. The additive migration `2026_11_12_000001_add_operation_observation.php` must run before invoking this extension. A lost response without saved proof stays ambiguous even if a later matching Coupon appears: it cannot establish the original Discount identity. Recovery only reads and retains the same command/reservation; expiry never releases uncertainty.

`Subscription::removeFreePeriod(string $actionKey, string $originalActionKey): Subscription` is a separate explicit financial decision. It requires that original succeeded command and the same currently observed Discount identity/bounds, then submits an empty subscription-level discount set and confirms its removal. A different/unconfirmed discount is refused. Natural CUSTOM expiry is provider-owned; no local timer submits removal or fabricates expiry confirmation. Removing a discount early does not move the application's separately persisted entitlement date.

A following tier can be submitted with `updateItemsForNextCycle` before its own confirmed renewal boundary while the Coupon remains applied; persist application entitlement dates independently. Local due plans retain subscription/item discount observations under the [versioned transition contract](#adoption-amounts-and-provider-routing). A changed or naturally removed discount blocks an unattempted plan; cancel/recreate it after canonical review. Neither strategy promises an atomic Coupon-expiry/renewal boundary, prepaid-service extension, waiver/refund of an existing Invoice or successful zero-cash billing. Canonical Invoice amounts/transactions and account timing remain separate acceptance evidence. See [the selected provider contract](provider-contracts.md#native-coupon-free-periods) and [recipe](../examples/free-period.php).

### Dated subscription ending

`Subscription::cancelAt(string $actionKey, string|DateTimeInterface $endsAt, array $options, ?array $renewalBounds = null): Subscription` schedules the original owned generation through Subscription Update. Required options are explicit `default_proration_mode` (NONE/PRORATED/ALL) and `billing_action` (one of the SDK update actions); other options are refused. The payload sets `ends_at` and clears `duration`/`remaining_duration`. It preserves the provider's period-end flag rather than claiming a dated end sets it true.

A first write requires locally and canonically supported finite ACTIVE OUT_OF_BAND/AUTO_CHARGE, or explicitly indefinite AUTO_CHARGE in PENDING/IN_TRIAL/ACTIVE. It refuses other combinations to preserve the same-command restoration path. It also requires no existing schedule, a future end after the start and no extension beyond a finite original end. It uses the ordinary subscription mutex, stores original bounds and accepts the same explicit renewal-bound shape as `cancelAtPeriodEnd()`. Canonical exact date proof projects the scheduled access cap before reconciliation events dispatch. The cap survives omitted/null bounds and old observations. Restoration clears it only through original-command proof; its existing state/collection restrictions remain. Repeated action keys keep their original intent and recover through reads, including after the scheduled date passes.

Financial controls use the SDK update fields. They establish no package calculation or guaranteed refund, shortened-period charge, credit note, settlement or invoice timing. The immediate-cancel endpoint's `proration_behavior` is a different contract and is not used for a future timestamp. See [dated-end provider evidence](provider-contracts.md#dated-subscription-ending).

## Fixed first-charge discounts

`Subscription::applyFirstChargeDiscount(actionKey, couponId, amountOff, currency, boundary)` selects an owned active FLAT/ONCE Coupon with the consumer's exact positive amount/currency. Submit before the current confirmed future period end supplied as `boundary`. The original boundary, Coupon terms and financial intent are durable; canonical preflight protects current generation, source, collection, unchanged Coupon and empty subscription/item discount sets. It uses NONE/DEFER_CHARGE_AND_KEEP_CYCLE without changing items or renewal. The required released SDK includes this Coupon API; the existing 100-percent/CUSTOM helper remains unchanged.

The command confirms only the original Discount identity, amount/currency and creation/start, saved set-once from the response. Lost original proof stays ambiguous. `removeFirstChargeDiscount(actionKey, originalActionKey)` explicitly removes that same still-observed Discount; a missing/different Discount is refused. Removal does not reverse a prior Invoice or establish compensation, and no consumption flag is inferred from local time or omission. The provider describes ONCE as the first charge/Invoice, measured from the first billing cycle. Whether a newly applied ONCE Coupon affects any later Invoice on an already-ACTIVE Subscription with earlier Invoices remains unverified. If it does, which later Invoice receives it (including any intervening adjustment) also needs proof. Early submission does not establish atomic targeting; this command is an experimental bounded primitive until that provider/account contract is qualified under #101/#63.

`Subscription::firstChargeDiscountInvoice(originalActionKey, invoiceId, expectedTotal)` makes only remote reads for an explicitly identified original Invoice. It requires the saved original response Discount, matching canonical subscription/customer/currency/routing, exactly that Discount's amount attribution, the consumer's exact positive total including tax, and every Invoice line's service period starting at the saved renewal boundary. Complete line paging and a final unchanged FINALIZED financial read must succeed. This can confirm an attempted original apply and release its local mutex after the Discount disappears from current Subscription reads; prepared/failed operations and missing original response proof remain ineligible. A fenced final transaction rechecks the original operation, generation, customer and immutable proof. Current lifecycle or a replacement name generation does not invalidate positively proven historical fulfillment.

The result is an owned Invoice observation, not cash or settlement proof. A 15-unit FLAT reduction and approved 15-unit total can represent the paid remainder of a 30-unit Invoice without computing daily rates. Missing/early/foreign/competing evidence refuses the claim and does not authorize another remote mutation. The consumer persists commercial free dates and its financial evidence. Exact phase targeting and actual Invoice/tax effects still need account qualification.

## Owned Invoice credits

Credit Notes use `billing()->creditNotes()` in required released SDK v0.1.3 (source `33881b46d696435dfbd370ec371e1fef5452ba44`). An authorized owned `Invoice` supports three separate durable commands:

```php
$draft = $invoice->createCreditNote('earned-free/create', 'BEFORE_PAYMENT', 'GOODWILL_GESTURE');
$items = $invoice->addCreditNoteItems('earned-free/items', 'earned-free/create', [
    ['invoice_line_item_id' => $originalLineId, 'amount' => '15.00'],
]);
$final = $invoice->finalizeCreditNote('earned-free/finalize', 'earned-free/create', '15.00');
$credit = $invoice->creditNote('earned-free/create'); // Explicit canonical server-side observation.
```

Each command returns its durable `Operation`; `remote_id` is the original Credit Note, and `succeeded` describes that command's canonical postcondition. The application decides eligibility, free dates, exact credit amount and treatment of already-paid service. A 15.00 credit against a 30.00 unpaid Invoice leaves its paid remainder; these example amounts are application choices, never a package daily-rate calculation. The package preserves the original Subscription and renewal, and performs no subscription mutation. This adjusts an existing finalized Invoice; it does not schedule an unbilled free interval or establish a future Invoice's amount.

Creation requires FINALIZED plus UNPAID for BEFORE_PAYMENT, or PAID for AFTER_PAYMENT. `options` supports provider `memo`, `custom_reason` and metadata. Addition supports a nonempty list of explicit original `invoice_line_item_id` and exact positive `amount`, optional description/metadata, and omitted/false `tax_included`. Unassigned/group/quantity credits remain SDK workflows. The package verifies original Invoice/line ownership and retains the financial baseline, complete Credit Note lines and original intent encrypted before dispatch. Reserved operation/index metadata is sent directly on the Credit Note and its lines. Complete canonical reads must prove each original line identity, source line, exact amount and correlation; a matching total alone cannot release uncertainty. The correlated line proof is stored once in encrypted `Operation::observation`.

Finalization requires the original package-created DRAFT, only previously confirmed package-added lines, unchanged financial baselines, and an explicitly authorized exact expected total including provider tax. BEFORE_PAYMENT sends an empty body and confirms that total as the same Note's Invoice adjustment. AFTER_PAYMENT additionally requires explicit `refund_amount` and `out_of_band_amount`; canonical allocation must match. Out-of-band records an externally performed adjustment; these methods establish no native provider future-balance allocation. The consumer owns any credit ledger. FINALIZED does not establish refund success or cash settlement; inspect the canonical `refund_status` and independent financial evidence. No additional Payments refund is created.

All stages share an Invoice financial mutex and stable action/request identities; finalization sends no invented `request_id` field. Changed baselines block an unattempted stage; attempted stages recover through reads only, retaining the original lock until positively confirmed. Creation with a lost response can use `airwallex:operations --reconcile --id=... --remote-id=...` only when canonical metadata proves the original command. Line timeouts recover only through direct operation/index metadata and complete line proof. Missing or competing proof holds the original uncertainty. No stage is automatically replayed, voided, deleted or compensated. Historical Invoices stay under their original owner/context. These deterministic contracts require separately authorized account qualification under [#63](https://github.com/jojeringnax/airwallex-laravel/issues/63); partial-period parity remains open under [#54](https://github.com/jojeringnax/airwallex-laravel/issues/54) and [#101](https://github.com/jojeringnax/airwallex-laravel/issues/101).

## Operational API

Operational commands and their exact options are defined in [webhooks and recovery](operations.md#bounded-commands). Each uses bounded batches, context filtering and safe progress identifiers. Recovery never submits prepared intents or repeats remote mutations. Inspect acknowledged item effects separately from unknown HTTP outcomes. Operator candidate association for unknown-ID subscription/checkout creation still requires canonical identity, customer, routing and reserved metadata proof. Queue workers, listener idempotency, scheduling, body retention and offboarding procedures are in the same reference.

Recurring `airwallex:sweep` persists progress per immutable owning context/resource family and checkpoints failed rows as attempted work before moving on. `Services\SweepRegistry::register(Support\SweepFamily $family)` extends read-only sweeps for additional contexts. Each value supplies `name`, `environment`, `ownerType`, `ownerId`, `query` (context-filtered Eloquent Builder closure) and `process` (Model → bool completion closure). Family names are unique in the scoped registry; rebuilding the registry after a worker scope reset preserves database progress. The current operation family excludes never-attempted `prepared` intents. Completion of a scan is independent of confirmation of every retained resource.

Optional `airwallex.webhook.queue_connection` and `airwallex.events.queue_connection` accept existing Laravel queue connection names; null preserves application-default routing. Their `queue` keys still select queue names independently. Both are validated before job dispatch after durable acceptance/commit, so invalid routing retains recoverable rows. Direct recovery commands retain their synchronous behavior. Database queue/cache/lock configuration and queued-listener retry ownership are documented in [operations](operations.md#receipt-and-event-delivery).

## Adoption amounts and provider routing

`Subscription::updateItemsForNextCycle(string $actionKey, array $items, string $boundary): Subscription` submits the native `NONE` / `DEFER_CHARGE_AND_KEEP_CYCLE` request before the exact confirmed ACTIVE period end or IN_TRIAL trial end. The original boundary is durable command intent, independently rechecked before every first dispatch and after source preflight. The current name generation must own the subscription and have no pending cancellation. An elapsed/changed boundary refuses an unattempted write; an attempted original command only recovers, including after the boundary. Canonical item observation confirms item projection, never the later Invoice or application entitlement. Persist application entitlement dates separately before invoking the [recipe](../examples/next-cycle-change.php).

`Subscription::scheduleTransition(actionKey, effectiveAt, items, options, expiresAt)` stores a single pending item transition for the current subscription generation. Effective/expiry times are exact timezone-bearing strings; expiry is an explicit allowed execution window. Options require explicit proration and billing action. The stored source shape includes item identities/prices/quantities, source/collection and auto-renew bounds. New plans use shape version 3, also retaining currency, billing anchor, cadence, total duration, payment due days, automatic/default tax settings and each item's tax override. A changed or omitted previously observed control blocks the first write; normal current-period rollover and the next billing date do not change this stable shape. Versions 1 and 2 retain their original fingerprints and prepared command identities; cancel/recreate an unattempted old plan to adopt the new guards. No migration or dependency change is required.

New plans additionally require their intended effective time to fall within the canonically observed current billing cycle at first dispatch; a skipped cycle or stale cycle observation blocks the action even within a generous expiry window. Future plans may span earlier cycles while waiting, but their first write belongs to the cycle containing the intended due time. The effective/expiry window is rechecked after preflight and immediately before the first write, including a clock correction back before the due time. Attempted commands retain read-only recovery past these dates and across later financial changes.

`SubscriptionTransition::run()` submits once when due and canonically ACTIVE; late/changed/unsupported state becomes blocked, attempted uncertainty ambiguous. `cancel()` and `replace(actionKey, effectiveAt, items, options, expiresAt)` are atomic only before an attempted financial action, retaining historical plan records. Cancellation/expiry never releases an ambiguous hold. Local due execution can be late and is distinct from native next-cycle submission: sending NONE after renewal may defer fees to the following cycle. It cannot promise an atomic provider boundary or an ACTIVE billing holiday.

`Subscription::restoreRenewal(string $actionKey, string $scheduleActionKey): Subscription` reverses a pending cancellation on the same owned generation. `cancelAtPeriodEnd(string $actionKey, ?array $renewalBounds = null)` saves the original canonical fields before scheduling. A finite original `ends_at` is captured automatically. For indefinite AUTO_CHARGE renewal, the caller supplies its known original intent explicitly as `['duration' => null, 'remaining_duration' => null, 'ends_at' => null]`; omission alone cannot establish that intent. Contradictory finite evidence is rejected. Changed explicit intent with the same action key conflicts; existing one-argument finite calls and recorded finite operations remain compatible. Old/imported scheduled records without saved original intent stay ineligible.

Supported restoration combinations are finite ACTIVE OUT_OF_BAND without a source, finite ACTIVE AUTO_CHARGE, and originally indefinite AUTO_CHARGE in PENDING, IN_TRIAL, ACTIVE or UNPAID. The saved state, collection method and source must still match before the first write; AUTO_CHARGE additionally requires a freshly owned Source. The current generation, latest scheduling action and future confirmed cancellation cap are checked. Restoration has a distinct durable action/request ID, preserves items/source and supplies false plus the original finite end or explicit null triplet.

Canonical confirmation requires false, unchanged source/collection and the intended bounds. For indefinite intent, omitted or explicit-null optional limit fields are accepted only together with that original command proof; a positive or malformed limit keeps the action ambiguous. Confirmation atomically clears `scheduled_ends_at` and, for indefinite restoration, the retained local `ends_at` before recording and dispatching the reconciliation event; raw snapshots preserve actual omission/null. Ordinary reconciliation continues to retain prior positive dates. This proves the scoped reversal, not unlimited future recurrence. PENDING/UNPAID retain their default access rules. A timeout or contradictory result holds the cap and original command; recovery only reads. Already-CANCELLED generations cannot be reactivated. [Provider observations](provider-contracts.md#renewal-restoration) establish the supported combinations independently from installed deterministic qualification.

The application boundary converts its integer minor-unit representation to exact decimal strings using an explicitly verified currency exponent; the SDK preserves the resulting major-unit value. For exponent 2, `"12345"` becomes `"123.45"`; exponent 0 retains `"12345"`; exponent 3 becomes `"12.345"`. Conversion uses digit/string operations, never floats, locale formatting or scientific notation. Reject unknown currencies, unsupported exponents, fractional minor units and out-of-range business amounts before command creation; reverse conversion rejects excess nonzero fractional precision rather than rounding. Zero is handled according to the [consumer scope](scope.md#full-provider-adoption-contract), never as invented provider success. The application owns any currency table/version and must verify the selected currency and method with the provider.

Billing organization and Payments account are independent immutable contexts. Separate mapping types, command identities, remote IDs and webhook routes prevent accidental cross-family adoption even where provider IDs have the same spelling. Consumer ledgers key deduplication by provider + environment + owning context + canonical financial resource ID + financial event type, not browser status or webhook event ID alone. Old-provider history/refunds stay routed to their original provider.

## Unknown creation retries

[Creation retry policy](operations.md#retrying-an-unknown-creation) permits a new creation key to supersede an attempted unknown-ID creation, including a still in-flight original. `superseded` is an unknown provider outcome, never a noncreation claim. Same-key dispatch remains at most one package attempt. Additive nullable `retry_release` columns on both Operation tables are encrypted, hidden and set once. They retain actor/reason/time/replacement-key audit. Late locators are quarantined and cannot replace current mappings.

Payments Intents retain immutable merchant order identity for history. The environment/account unique key now uses nullable `order_reservation`; existing rows are backfilled from `merchant_order_id`, while superseded unknown creations release only their own reservation. Known provider resources and positively observed refundable amounts keep their existing guards. `Services\CreationRetries::allowRetry(Models\Operation|Payments\Models\Operation $operation, string $actor, string $reason): void` exposes the same explicit local release and enforces configured context. The application authorizes its actor and operation.

## Billing Source creation from Payments

`Payments\Instruments::createBillingSource(Payments\Models\Customer $customer, string $consentId, Models\Customer $billingCustomer, string $actionKey): PaymentSource` creates a Source from a canonically verified merchant/unscheduled Consent and card Method. The Customers must map the same billable/environment; the Billing collector equals the Payments account. A `payment_source.create` Billing Operation freezes the account, consent, Method and creation correlation before the POST. Canonical Source reads prove its saved customer/collector/Method/correlation before success. Same-key calls and `RecoveryManager::operation()` recover through reads, including an explicit correlated candidate when the response ID was lost. `RecoveryManager::operation()` consequently returns a Billing model or a `PaymentSource` value object.

Source history remains readable after instrument revocation, without claiming present eligibility. Revocation observations use the existing durable `PaymentObserved` outbox and optional string `revoked_at`. `airwallex.payments.events.instrument_revoked_handler` defaults to null; a configured class implements `Contracts\InstrumentRevocationHandler::handle(PaymentObserved $event): void`. It handles local revocation, canonical Consent DISABLED and Method DISABLED observations, with at-least-once delivery and the same stable event identity. Consumer-selected subscription changes use explicit durable commands and financial controls; no cascade is inferred from provider behavior.
