# Laravel Airwallex

Read [scope](docs/scope.md) before changing capabilities, [public contracts](docs/contracts.md) before changing interfaces/persistence, and [provider evidence](docs/provider-contracts.md) before API-sensitive work. [Compatibility](docs/compatibility.md) owns support/distribution policy. GitHub [release tracker #1](https://github.com/jojeringnax/airwallex-laravel/issues/1) and [project #3](https://github.com/users/jojeringnax/projects/3) own execution status and native dependencies.

Inspect the working tree, relevant issue criteria, comments and PRs before editing. Preserve unrelated/concurrent work. Keep authentication, HTTP, API validation, payload precision and signature verification in the SDK; the sibling SDK is read-only for this release. Verify provider-sensitive behavior against official Airwallex sources and the selected SDK version, distinguishing documented contracts from account observations.

For substantive implementation and documentation, obtain independent agent review using the actual diff, acceptance criteria and prerequisite evidence; fix findings and recheck affected behavior. Run meaningful deterministic checks without credentials. Keep secrets, customer profiles and client secrets out of commits and diagnostics. Sandbox requires explicit sandbox configuration and ownership controls; live financial operations are outside this work.

Use installed warrior-skills under `.agents/skills`: writing-for-agents for instructions, writing-docs for documentation, open-pr for PRs, create-issues for planning repairs/questions. If unavailable, consult [warrior-skills](https://github.com/jojeringnax/warrior-skills). These skills do not grant publication permission.

The release implementation request authorizes scoped codex/ branches, commits, pushes, PRs and issue/project maintenance. Material decisions follow its non-blocking question-issue policy: record evidence, alternatives, provisional choice, consequences and change cost, implement a viable assumption and leave the question open. Revisit comments at milestone checkpoints. Merging, default-branch pushes, shared force-pushes, tags, publication and production operations require separate authorization.

Maintain a tested cumulative integration branch. Use focused stacked PRs with explicit bases. Awaiting-merge work remains open; distinguish validated implementation from delivery. Record resumable checkpoints in GitHub with branch/commit, active work, checks, findings, assumptions and next action.
